# 部署与发布规范（对外版）

> 说明我们的版本管理、发布、留痕与回滚做法。本文为方法论，不含具体环境信息与凭据。
> 版本：2026-10 对外版 v1.0

---

## 一、版本号约定

采用 `git describe --tags --always` 生成可追溯版本串：

| 情形 | 版本串示例 |
|---|---|
| HEAD 位于 tag | `v1.0.0` |
| tag 之后 N 个提交 | `v1.0.0-2-g0b9f8d9` |
| 无 tag | 短提交号 |
| 有未提交改动 | `v1.0.0-dirty` |

- **语义化版本**：`X` 不兼容变更，`Y` 兼容的新功能，`Z` 兼容的问题修复。
- tag 在**发布时**打，并按"版本线"独立打标；引用版本时**同时注明版本线**。
- 产品版本自 `v1.0.0` 起，不使用上游开源项目的版本串。

---

## 二、各组件打戳

| 组件 | 打戳方式 | 产物 |
|---|---|---|
| 实时语音服务端（Python） | 发布脚本生成 `version.txt` | 服务启动时打印到日志 |
| 管理后台（Java） | 构建期插件生成版本描述文件 ＋ MANIFEST 版本字段 | 包内文件 |
| Web 控制台（前端） | 构建后生成 `version.json` | 静态产物目录 |

打戳产物均为生成物，不纳入版本库。

**硬规则**：**先打 tag，再构建**——否则产物会带错误版本。

---

## 三、发布流程

1. 确认改动 → 提交并打 tag；
2. 构建各组件（后台、前端、服务端）；
3. 对服务端与前端执行打戳；
4. 部署并留痕（见第四节）；
5. 只读巡检确认线上版本（见第五节）。

---

## 四、部署留痕

每次部署追加一行记录：**时间 ｜ 环境 ｜ 组件 ｜ 版本 ｜ 提交号 ｜ 包校验值 ｜ 备份位置 ｜ 执行人**。

"版本可追溯、包可校验、有备份路径"是交付验收与后续排障的前提。

---

## 五、只读巡检

提供**只读巡检脚本**，一次输出各组件：版本串、提交号、进程与端口状态、产物校验值。
巡检脚本不修改任何文件，可在客户环境安全执行。

---

## 六、部署时的保留清单

部署只替换代码与构建产物；以下内容**一律不覆盖**（客户现场数据与配置）：

```
服务端配置文件 / 外置覆盖配置
运行数据目录（含生成的文档、临时文件）
模型与素材目录
运行环境（虚拟环境 / 依赖目录）
版本库目录
编译缓存（传输前清理，避免陈旧字节码）
```

---

## 七、回滚

| 组件 | 回滚方式 |
|---|---|
| 实时语音服务端 | 还原备份目录 → 重启服务 |
| 管理后台 | 还原上一版本包 → 重启服务 |
| Web 控制台 | 还原旧静态产物目录（无需重启） |

**无数据库迁移时，回滚即还原代码**；涉及数据库结构迁移时，**先备份数据库再升级**。

---

## 八、待改进项（对外透明）

- 当前为**人工打包上传**，尚未接入自动化流水线（CI/CD）；
- 目标：由发布仓库产出带版本号的交付包，配合校验值与变更日志一并归档。

> 我们认为"能不能把版本讲清楚"是私有化交付的底线能力，因此把现状与改进方向一并公开。
